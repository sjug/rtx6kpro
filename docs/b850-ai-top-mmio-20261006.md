# Enabling four RTX PRO 6000 GPUs through the B850 AI TOP hidden MMIO setting

## Result and boundary

The F13d firmware contains a real consumer of the hidden `Above 4GB MMIO Limit`
setting. `NbPei` reads the matching Setup byte and sets a platform configuration
database (PCD) value that the Granite Ridge resource-allocation code reads.
This is stronger evidence than a setup-menu string alone. Following the static
inspection, the user confirmed physical recovery access and intentional removal
of the discrete GPUs. A one-byte change from 40 to 41 bits was applied and verified,
then a reboot was issued. The changed value persisted and the high PCIe root
window moved to `0x10000000000-0x1ffffffffff`, exactly 1 TiB of address space
between the 1 TiB and 2 TiB boundaries. The hidden setting is effective on this
host with F13d and the 9800X3D. Subsequent boots with two and then four discrete
GPUs succeeded. All four RTX PRO 6000 Blackwell Max-Q cards have their physical
BARs assigned, including a 128 GiB Resizable BAR per card, and all four are
recognized by the NVIDIA driver. GPU workload qualification was not performed.
No firmware image was patched or flashed, and no boot options were changed.

The visible menu location remains unconfirmed. The user's BIOS search finds
Above 4G Decoding but not the MMIO limit. The internal form hierarchy is Chipset
-> North Bridge -> Above 4GB MMIO Limit; it is not a verified navigation path in
Gigabyte's graphical interface.

## What changed, and what did not

We changed a BIOS **configuration value**, not the BIOS **firmware image**.
The distinction matters: saying “no BIOS changes” would be inaccurate if it meant
that every firmware setting remained unchanged.

The existing F13d firmware already implements this MMIO limit. Its setup form
contains the setting, and its boot-time executable code consumes it. We changed
one byte in the persistent UEFI `Setup` variable from decimal 40 to decimal 41,
using Linux's efivarfs interface. On the next boot, the original firmware read
that value and performed its normal resource allocation with a higher ceiling.

There was no patched ROM, modified firmware executable, Q-Flash operation, or
replacement BIOS. The supplied BIOS archive was used for offline inspection.
The setting was not made visible in the graphical setup interface. Above 4G
Decoding was already enabled. No kernel command-line change was needed.

The end-to-end path was:

```text
Linux efivarfs write
    -> persistent UEFI Setup variable, payload byte 0x1b3 = 41
    -> reboot
    -> NbPei reads Setup and computes (1 << 41) - 1
    -> platform resource code uses the new address ceiling
    -> firmware exposes a high PCI root window from 1 TiB to 2 TiB
    -> four GPUs receive their physical BAR allocations
    -> Linux and the NVIDIA driver enumerate all four cards
```

## Why this setting mattered

A PCI BAR describes an address range through which software accesses a device.
MMIO address space is not an allocation of system RAM. The 128 GiB GPU BAR does
not mean that a card has 128 GiB of VRAM: these cards report 97,887 MiB of usable
framebuffer memory through `nvidia-smi`, while their full Resizable BAR aperture
is a power-of-two 128 GiB window.

Above 4G Decoding permits device memory mappings above the 4 GiB address boundary.
It does not by itself select a sufficiently high platform allocation ceiling.
The separate hidden MMIO limit controls that ceiling. Its labels describe powers
of two in bytes: the option labelled 1 TB corresponds to 40 bits, or 1 TiB; the
option labelled 2 TB corresponds to 41 bits, or 2 TiB. This report uses GiB/TiB
for exact binary quantities.

Even a large total free range is insufficient if aligned BARs cannot be packed
inside the bridge windows. Here each GPU needs a 128 GiB aligned BAR plus a
64 MiB BAR and a 32 MiB BAR. The observed firmware layout places the two small
BARs immediately after the large one. That creates a 128 GiB + 96 MiB span per
card, with the next large BAR starting at the following available 128 GiB boundary.

## Executable consumer

`NbPei` is an IA32 TE executable, not an x86-64 executable. Offsets below are
relative to the extracted TE body; disassemble with `objdump -D -b binary -m i386
-Mintel` rather than treating it as an ordinary PE executable.

1. The routine at body offset `0x38f` allocates a Setup buffer and calls the
   read-only variable PPI. At `0x39b`, the requested size is `0x23b`.
2. At `0x3d8` and `0x3dd`, the arguments identify the exact Setup GUID above and
   the UTF-16 string `Setup`. These pointers map to body offsets `0x4d8` and
   `0x4e8` respectively (TE address adjustment `0x09a3edf8`).
3. At `0x3c9`, the buffer starts at the then-current `esp+0x18`. There is a
   temporary push at `0x3f0`; therefore the read at `0x3fe`, `[esp+0x1cf]`, is
   exactly buffer offset `0x1b3`, not a different setting. The byte is copied
   to output structure offset 4. Read failure falls back to `0x28`.
4. The local hook dispatcher at `0x364` calls a stub at `0x44b` (`ret 0`) and
   has a terminating null function-pointer entry. It does not alter this value.
5. The caller at `0x247` invokes the reader. At `0x24c` it loads the returned
   byte, and helper `0x319` computes a 64-bit `1 << bits`. At `0x25a`/`0x25d`
   it subtracts one.
6. At `0x267`, token `0x495` is passed to the PCD PPI's `Set64` entry at
   table offset `0x48`. The located PPI GUID is
   `06e81c58-4ad7-44bc-8390-f10265f72480`.
7. The same bit count is also placed in the CPU HOB's memory-address-width field
   at `0x278`. Changing it is consequently not just changing a menu label.

PCD function-table identification is grounded in the
[EDK II PCD PPI definition](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Ppi/Pcd.h):
on IA32, Get64 is offset `0x10` and Set64 is offset `0x48`.

## Allocation readers and constraints

`AmdSocAm5GnrPei` reads token `0x495` via PCD Get64 at TE body offsets
`0x3290`/`0x32a8` and `0x5eaf`/`0x5ec7`. Its PCD lookup uses the same PPI GUID.
The surrounding code computes a CPU-address-width limit, accounts for the
encryption-related address-bit reduction, compares it with the configured limit,
and uses the smaller ceiling in resource calculations.

`AmdFabricRplDxe` also reads `0x495` at RVA `0x66b1`. Code at
`0x66eb` through `0x6754` explicitly handles ranges on either side of
`0xfd00000000` and `0x10000000000`. This is consistent with the 12 GiB reserved
hole below 1 TiB observed on the live host. It compares the available lower and
upper ranges and may choose the larger one. Increasing the limit may therefore
relocate the chosen aperture above 1 TiB, rather than simply extend its current
upper end.

This establishes a static allocation path, not proof that every possible platform
callback or later override is absent. The named PCD symbol was not recovered;
`0x495` is an image-specific token identifier, not a portable setting name.

## Controlled live test

A one-step increase from 40 to 41 bits (`0x28` to `0x29`) was performed after the
user authorized necessary work and confirmed physical access and GPU removal.
This initial test isolated the control with the discrete GPUs removed. A fresh Setup backup
matched the earlier hash. The proposed 575-byte efivarfs representation differed
at exactly one byte: file offset 439, payload offset `0x1b3`.

The write checked DMI board name, F13d BIOS version, payload length, attributes,
and the entire original-variable SHA-256 before proceeding. It temporarily cleared
the efivarfs immutable flag, wrote the complete attributes-plus-payload buffer
without truncating/deleting the variable, verified exact readback, and restored
the immutable flag in a finally block. Firmware accepted the runtime write.

```text
MMIO-UPDATE-VERIFIED bits=41
sha256=8d4ea875c3de6bdfb18d51b0ef49fa4507b07591f8c68b29ba0e17a2b327aed0
Setup immutable protection restored
```

The pre-test snapshot is `/tmp/codex-nous-Setup-before-test.efivar` on the
workstation. The candidate snapshot is `/tmp/codex-nous-Setup-41bit-candidate.efivar`.
Before reboot, MicroShift was inactive and the current user's Podman container
list was empty. Pre-test boot ID: `2b44468c-f9a5-405f-873a-7421a1ba7753`.
The machine was rebooted with `systemctl reboot` and returned over SSH. A saved
variable file is not a full firmware recovery backup, and
CMOS/Q-Flash behavior for resetting this variable has not been tested.

### Post-boot verification: pass

New boot ID: `2ef7f22f-9b78-49c5-85db-0ddf3cd63f7e`.
BIOS remains F13d. The efivarfs immutable flag is set. The complete live Setup
variable still hashes to the candidate hash above, so the only change from the
pre-test snapshot remains payload byte `0x1b3`, `0x28 -> 0x29`.

```text
pci_bus 0000:00: root bus resource [mem 0x10000000000-0x1ffffffffff window]
```

Both `/proc/iomem` and the new boot's kernel log show this window. No matching
BAR no-space/failure, failed assignment, or resource collision messages appeared
in the new boot. SSH returned; no discrete GPUs were present for this test.

| Observation | Before, 40-bit | After, 41-bit |
| --- | --- | --- |
| High root window start | `0x1060000000` (65.5 GiB) | `0x10000000000` (1 TiB) |
| High root window end, inclusive | `0xfcffffffff` | `0x1ffffffffff` |
| Usable root-window size | 946.5 GiB | 1024 GiB |
| Configured address ceiling | 1 TiB | 2 TiB |

The observed result confirms the earlier warning: this is an address-limit
control, not a request for an aperture of the labelled size. The allocator chose
the larger contiguous range above the reserved hole. The host is left at 41 bits;
40 bits is the original value for rollback. Larger values remain untested, and the visible BIOS search still has no verified
path to the item. The subsequent four-GPU result is documented below.

## How the Linux write reached persistent firmware configuration

The variable is identified by both its name and its vendor GUID:

```text
/sys/firmware/efi/efivars/Setup-ec87d643-eba4-4bb5-a1e5-3f3e36b20da9
```

This is a firmware-backed filesystem entry, not an ordinary disk file. Linux
provides access to UEFI variable services through efivarfs. A successful write
updates the firmware variable store. The captured attributes were `0x00000007`:
nonvolatile, boot-service accessible, and runtime accessible. Nonvolatile storage
explains why the setting survives reboot; runtime access permits the operating
system to access it after boot. The exact physical backing location of the
variable store was not independently mapped in this investigation.

The Linux representation contains four attribute bytes followed by the variable
payload. Thus the IFR payload offset `0x1b3` becomes file offset `0x1b7`, decimal
439. The 571-byte Setup payload becomes a 575-byte efivarfs entry. Confusing these
offsets would change a different setting. Linux documents this representation
and its immutable protection for nonstandard variables in the
[efivarfs documentation](https://docs.kernel.org/filesystems/efivarfs.html).

The actual operation preserved the entire variable except that one byte:

```text
Attributes:             07 00 00 00       unchanged
Payload length:         0x23b bytes      unchanged
Payload offset 0x1b3:   28 -> 29         hexadecimal
Meaning:                40 -> 41         address bits
Computed ceiling:       2^40-1 -> 2^41-1 inclusive
```

The write was guarded by the board and BIOS identity, expected length and
attributes, and the SHA-256 of the complete original variable. It opened the
existing entry for writing without truncation and submitted the complete
attributes-plus-payload representation. It did not delete and recreate Setup.
Immediate readback had to match the proposed bytes exactly. The immutable flag
was temporarily cleared only to permit the write and restored afterward.

That flag is a Linux filesystem safeguard, not the persistence mechanism and not
a guarantee that firmware will never change the variable. Loading setup defaults
or installing another firmware version may reset the value or change its layout.
The offset and hashes in this report are specific to the inspected F13d layout;
they are not a generic Gigabyte BIOS editing recipe.

A saved variable snapshot is also not a tested recovery procedure. The initial
write was performed only after physical recovery access was confirmed. We have
not tested whether clearing CMOS or using Q-Flash restores this particular
variable. No additional firmware write is needed to inspect the current state.

## Four-GPU boot: observed allocation matches the prediction

After the initial GPU-free verification, the user booted with two GPUs and then
with four. The four-GPU boot was inspected over SSH using `lspci`, `nvidia-smi`,
`/proc/iomem`, and the current boot's kernel journal. Its boot ID is:

```text
65d55f09-e806-4cd9-9502-8f7bbeb9ecb6
```

A subsequent read of the Setup entry on that boot still returns decimal `41` at
file offset 439, and `lsattr` still shows the immutable flag. This later check
verified the setting byte, not another full-variable hash comparison.

All four devices are NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition,
PCI ID `10de:2bb4`. All four use the NVIDIA driver and report 97,887 MiB each
through `nvidia-smi`. The loaded NVIDIA kernel module reports version 610.57.04.

| GPU | PCI address | 128 GiB BAR address | Large BAR starts | Small BARs start |
| --- | --- | --- | --- | --- |
| 0 | `0000:03:00.0` | `0x1c000000000` | 1792 GiB | 1920 GiB |
| 1 | `0000:04:00.0` | `0x18000000000` | 1536 GiB | 1664 GiB |
| 2 | `0000:05:00.0` | `0x14000000000` | 1280 GiB | 1408 GiB |
| 3 | `0000:06:00.0` | `0x10000000000` | 1024 GiB | 1152 GiB |

For each card the small allocations are 64 MiB followed immediately by 32 MiB.
All four physical Resizable BAR capabilities report a current size of 128 GiB.
The physical GPU BARs total **512 GiB + 384 MiB**. Their enclosing upstream PCI
branch spans `0x10000000000-0x1e0061fffff`, or **896 GiB + 98 MiB**, including
alignment gaps and other bridge/device allocations. Nested bridge ranges must
not be added together: they describe overlapping containment, not independent
consumption.

The high root window remains:

```text
10000000000-1ffffffffff : PCI Bus 0000:00
```

It is exactly 1 TiB of address space between 1024 and 2048 GiB. The 2 TiB setting
is the ceiling, not the size of this window.

### Why the extra address bit makes four cards fit

With the old aperture, aligned 128 GiB starts were available at 128, 256, 384,
512, 640, and 768 GiB. A start at 896 GiB would end at 1024 GiB, beyond the old
1012 GiB upper boundary, even before adding the small BARs.

Under the observed packing pattern, one card consumes a large aligned window
plus a small tail that prevents use of the immediately adjacent aligned window.
Descending placements would therefore be 768, 512, and 256 GiB. A fourth would
need to start at zero, below the aperture's 65.5 GiB lower boundary. This is an
allocation-pattern explanation, not a universal three-card limit for every
possible firmware packing strategy.

The new aperture has eight complete 128 GiB slots. The four starts at 1792,
1536, 1280, and 1024 GiB match the prediction exactly. Each small tail fits before
the next occupied large window or the top of the root aperture.

The aperture grew only from 946.5 GiB to 1024 GiB in total size. Its relocation
to aligned boundaries is crucial: it gained two usable 128 GiB slots even though
its total size grew by only 77.5 GiB. This is why simply comparing total BAR bytes
with total aperture bytes missed the problem.

The successful boot establishes that the changed setting supports this four-card
configuration. We did not reproduce the previous four-card hang under the old
setting with a firmware allocation trace, so its exact failure point remains
inferred rather than directly observed.

## Why SR-IOV allocation warnings remain

The boot still contains `VF BAR ... can't assign; no space` messages. These are
for virtual-function resources, not the successfully assigned physical GPU BARs.
Each GPU advertises 48 possible VFs, while reporting zero enabled VFs and
`IOVCtl: Enable-`. That is a statement about the devices' current state; we did
not independently verify the motherboard's graphical SR-IOV switch.

Per GPU, the advertised VF ranges request:

| VF resource | Per VF | Total for 48 VFs |
| --- | --- | --- |
| VF BAR 0 | 256 KiB | 12 MiB |
| VF BAR 2 | 4 GiB | 192 GiB |
| VF BAR 4 | 32 MiB | 1.5 GiB |

Linux discovers and sizes these resources even when no VFs are enabled. The
upstream Linux 5.14 implementation multiplies the per-VF resource size by the
total advertised VF count during SR-IOV initialization, and the PCI allocator
handles VF requests as optional resource additions in its reallocation path.
See [iov.c](https://github.com/torvalds/linux/blob/v5.14/drivers/pci/iov.c) and
[setup-bus.c](https://github.com/torvalds/linux/blob/v5.14/drivers/pci/setup-bus.c).
These references explain the upstream mechanism; the host runs a downstream
RHEL kernel, whose exact patched source was not audited here.

Those extra reservations fail and remain unassigned. They do not consume the
requested space, and they do not indicate that SR-IOV is secretly enabled.
Every physical GPU BAR is assigned. Enabling VFs would require a separate
resource-allocation investigation.

## Verification boundaries and read-only checks

What was demonstrated:

- The F13d setting has an executable consumer in the platform allocation path.
- Changing only its byte persisted across reboot and changed the root aperture.
- Four GPUs boot with the predicted BAR placements and full 128 GiB ReBAR windows.
- Linux and the NVIDIA driver recognize all four GPUs.
- The inspected boot log contains no NVIDIA Xid errors; the observed BAR
  allocation failures concern unused VF resources.

What was not tested: sustained CUDA workloads, multi-GPU collectives or P2P,
performance, long-term stability, larger MMIO values, and recovery behavior after
resetting firmware settings. The cards reported x16 endpoint links at 2.5 GT/s
at inspection time; this idle observation does not establish loaded link speed
or upstream-switch bandwidth.

These commands inspect the current configuration without changing it:

```bash
ssh -n nous 'nvidia-smi --query-gpu=index,name,pci.bus_id,memory.total --format=csv'
ssh -n nous 'sudo -n lspci -Dvv -d 10de:2bb4'
ssh -n nous 'sudo -n cat /proc/iomem'
ssh -n nous 'sudo -n journalctl -k -b --no-pager'
ssh -n nous 'sudo -n od -An -tu1 -j 439 -N 1 /sys/firmware/efi/efivars/Setup-ec87d643-eba4-4bb5-a1e5-3f3e36b20da9'
```

The final command is specific to the verified F13d variable layout and should
print `41`. Temporary extraction files and snapshots referenced above are working
evidence under `/tmp`, not durable backup storage. The identities, hashes,
firmware offsets, and observed results are recorded inline here so that the
report does not depend on those temporary files remaining available.
